更新日期：2026-10-02（香港时间）。项目根目录：`C:\Users\blackvccat\Desktop\巴黎街区素材 4\巴黎街区素材\paris-builder`。

本报告以“玩家与agent对话，从初步需求出发，先造型符合风格外观，再细节符合训练手法，最后完善整栋交付”为主线，解释已有系统、材料、当前构图改造和验收边界。历史研究结论、历史候选验证、本轮实现与本轮最终验收分别记录；任何旧 PASS 都不能转移给新候选。本轮 P2 收据尚未闭合的条目标为“待本轮收据”，后续应按最终 `.schem` 的哈希补齐。

## 1. 项目最终要做什么

目标是让玩家通过对话表达初步需求，agent理解并持续吸收玩家补充，研究建筑风格、地块与用途，先形成符合所需风格的造型，再把训练得到的真实建造手法用于细节，最后完善整栋并导出可在Minecraft使用的`.schem`。全过程保存可复查的需求、来源、装配与评审证据。巴黎建筑是首个验证案例，不应成为只会重复一栋巴黎楼的模板系统。

输入不能只有“法国风格”几个字。系统需要理解建筑类型、临街方向、相邻建筑、尺度预算、入口、主要观察距离、目标版本与用户技法偏好。输出也不能只有一张好看的正视图：整栋的体量、立面、转角、屋面、收口和每个可见方向都要成立。

项目同时交付生成系统与建筑实例。构件库扩大、技术检查通过或网页能启动，分别证明系统的不同环节可用；建筑是否有主次、有纵深、具有真实巴黎建筑的组织方法，以及是否满足用户审美，需要继续通过实际产物评审证明。

### 用户标准与“能搬”和“能创”的差距

用户要求的写实感来自具体建造方法：门叶薄窗面、冻结墙肢、强制楼梯转角、分层窗套、阳台牛腿、檐口齿饰、老虎窗颊板与烟囱收头都要有建筑用途。把整墙挖洞再贴边框，或用一层深色壳表示屋顶，不能替代这些构造。

但是，即使所有源件都被准确搬进新场景，也可能只得到一面重复窗墙。设计还必须决定哪些开间退后、哪些凸出，主层如何突出，转角与入口如何成为焦点，以及屋顶附属构件如何呼应下面的构图。源件保真回答“怎么做”，条件规则与构图选择回答“为什么放在这里”。

完整原创能力还需要在不同任务中形成可感知不同的有效方案、根据地块条件选择形态、在尺寸约束内选择兼容件、针对失败原因修改，并在全栋视角中保持统一；不意味着把多套不足方案交给玩家选。本轮P2只推进造型层中的一个增量：同源塔亭公寓的构图规则；独立装配楼存在不等于玩家交互到整栋交付的目标完成。

## 2. 知识与生成职责怎样分层

`WORKFLOW_STYLE_LEARNING.md` 将知识分为现实建筑原型、Minecraft 构件手法、建筑框架和实例四层。原型层记录风格关系，不出现具体方块或单栋坐标；手法层记录准确状态、深度和边界条件；框架层决定新建筑的组织；实例层保存选择路径、装配坐标和最终导出。

在单栋代码中，结构、立面与技法是三份独立职责，由装配入口协调：

| 层 | 主要模块 | 应决定的内容 | 约束 |
|---|---|---|---|
| 结构 | `src/paris_builder/house.py` | 地块轮廓、体量、两翼/院落、各面角色、楼层与屋顶边界 | 不用小装饰代替体量 |
| 立面 | `src/paris_builder/facade.py` | 开间、入口轴、凸退、层级、水平带与构图节奏 | 规则不绑定具体方块状态 |
| 技法 | `src/paris_builder/technique.py`、图谱件与装配器 | 用准确方块模型落实窗、店面、檐口、栏杆等 | 状态与来源要可追溯 |
| 单栋装配 | `src/paris_builder/design.py` | 协调布局与技法，选择 profile，生成实例 | 避免同一布局在多个入口复制 |
| 城市 | `src/paris_builder/city.py` | 街道、地块、邻居、共享边界与沿街变化 | 应调用单栋能力，不再自造一套窗墙 |

传统三层模块已有多种结构与立面组合。历史矩阵验证证明它们可组合并能生成开口、线脚等，不能证明每个组合达到当前真实建筑品质。图谱路径新增的设计契约应表达开间角色与相对进退，再由装配器选择具体源件；结构预算必须在落块前容纳这些选择。

## 3. 当前有两条生成路径

### 传统参数化路径

一般路径为 `design.build → house/facade/technique`。`reference_haussmann` 使用 `haussmann_reference.py` 的专门适配器，其中包含街屋与转角楼的构造规则。这条路径支撑旧 PAR-002、ATELIER 流程、阶段生成、技术验证与模型视觉评审。

它的优势是参数与阶段链已接入得较多，可以表达尺度、楼层和开口等变化。局限是部分技法仍为程序画出的符号，具有重复、挖洞贴框或全栋细节不充分的风险。旧候选曾通过文件与几何检查，仍被用户指出缺少调试棒建造手法，这正是图谱工作要补的缺口。

### 真人构件图谱路径

这条路径直接消费从真人源作品裁出的完整元素及派生件。`atlas_assembly.py` 负责来源校验、旋转、子裁、派生、落位、覆盖账目与回读；`atlas_street1.py` 承载首栋同源策略。屋面、窗带、阳台、檐口和塔亭使用真实件，参数化填充补齐结构与共墙。

其当前优势是构造状态真实、件与来源有逐格联系、装配损失能诊断。其局限是首栋仍依赖街区1成套语汇，层序与尺寸自由度受源件约束；它尚不是覆盖所有类型和全部变体的通用生成器。两条路径可以共用 `design.build` 的产品入口，但各自的 profile 语义与验收适配器必须明确。

## 6. 来源、清洗、派生与冻结状态纪律

每件应同时保存原范围 `source-crop.schem`、清洗件 `detail.schem`、`record.json`、注册表报告、NBT上下文与预览。记录包括当前源文件哈希、源坐标、原点、室外方向、语义角色、边界连接、支承与切面说明。源素材只读，历史库件不被新派生覆盖。

清洗不是把状态改成“正常”。已核对的版本差异是明确登记的 `minecraft:chain → minecraft:iron_chain` 改名，属性保留；空气按方块名称识别，不能以palette索引大于0判断。窗面门叶全部 `half=lower` 可能是原作者的薄模型手法，不能自动改成成对功能门。

旋转必须同时改变位置与方向状态；墙连接、楼梯inner/outer、门朝向和栏杆连接随件携带。子裁必须登记半开范围。原版替代例如 `create:cut_calcite_wall → minecraft:diorite_wall` 要另建派生件并重放操作、保留连接属性，原模组件继续作为研究证据。

装配入口不能只信 `compatible_vanilla=true`。当前装配器验证件哈希、主源哈希，并沿源坐标重建切片；派生要逐格重放与比较。每次落位有独立owner、位置、角色、裁齐范围、同状态重叠与异状态覆盖，最后从导出回读。

有限交接许可只解决有解释的结构叠放：两翼交界、同源带状件、老虎窗穿坡和烟囱坡脚等。整件丢失、场景出界、无法解释损失不能被总开关豁免。审计PASS仍需配合直接量测和目检，不能用账目完整证明构图漂亮。

`.schem`保存状态，不负责禁止粘贴器更新。特殊状态在游戏中的显示、邻接变化与区块重载稳定性，必须由用户使用目标版本和已验证粘贴方式检验；预览模型与注册表不能替代这一结果。

正式阶段链为 research→retrieval→frameworks→facades→tier2→tier3→delivery→game。阶段状态与证据登记在 `runs/<run>/workflow.json`，候选文件和评审绑定哈希；后台执行和会话记录与页面一致，刷新不能把正在运行或失败状态误报通过。

### 玩家主流程与本轮接线边界

| 玩家与agent的动作 | 对应阶段 | 必须闭合的结果 |
|---|---|---|
| 玩家给初步需求，agent理解、研究与补齐必要条件 | intent/research/retrieval | 对话中保留用途、风格、尺度、方向、参考与明确限制，修改累积到同一任务书 |
| 先造型，agent自己检查风格外观 | frameworks | 无细节掩饰的体量、凸退、层级、开间、转角和屋顶成立；不合格留在造型层修复 |
| 立面构图并装配训练手法 | facades/tier2 | 已通过造型稳定，选件服从布局，窗层/阳台/檐口/店面与屋面逐层落实 |
| 完善整栋并交付 | tier3/delivery | 全向、端头、共墙与屋顶交接完整，技术和品质收据绑定最终导出与下载包 |
| 玩家在游戏中确认 | game | 显示、冻结态、重载与实际建筑品质由玩家判定 |

当前`classify_turn`区分普通回复、任务书草稿与明确建造/修改意图；草稿分支不启动构建。`prepare_framework_contract`从对话重建完整任务书并累积后续纠正，模型命名的`confirmed_brief`是它对玩家已确认内容的读取，不等于新增一个系统可以代替玩家签认的审批。

只读代码核对发现，图谱P1接进`design.build`后尚未贯通这条链：规划目录仍只描述`reference_haussmann`，composition未传到intent；候选与交付重建缺少图谱`work_dir`；图谱`complete_kit`不随tier裁剪，会在造型阶段带入全部细节；现有split-v3又只量测北/东旧转角。这些需要在既有工作流修复，不能以另一个独立装配工具替代玩家流程。

现有 `candidate_search.py` 保存历史候选与incumbent，`/api/workflow/restore-best` 提供恢复入口。恢复产生新修订与新评审，不能继承历史通过；运行中不能同时恢复。服务不热加载，修改 `src/` 后需由同一控制聊天协调重启并确认无竞争作业。

新图谱“已进入design入口”与“网页全链能使用它”是不同完成条件。后者还要证明请求解析、profile选择、派生落盘目录、阶段语义、审计rows、几何适配器、模型评审、失败恢复和下载都消费同一实现。目前不能仅凭import或CLI成功报告这一产品闭环完成。

## 8. P1 已完成的接线与保留基线

P1将首栋策略从工具脚本移入 `src/paris_builder/atlas_street1.py`，`tools/build_atlas_house.py` 留作薄CLI。`design.build` 新增 `detail_profile='atlas_street1'` 分支，调用 `build_from_plan(plan, work_dir, tier)`；`tools/build_atlas_plan.py` 通过这个主入口生成plan驱动候选。

平铺基线按 `seed % 4` 选择 `(4,5,5,4)` 节距相位，在宽深预算内推导最大开间数，并保留北翼至少5、西翼至少4的底线。历史最小包络为34×50×31；层序仍来自街区1源件：拱廊、标准窗、下阳台、贵族通高窗、上阳台、檐口窗带与曼萨德。

该profile的tier语义是 `complete_kit`：接受阶段值，但不抽掉源套件中的整层构造。任意层数、屋顶高度、切角和开间模数不能假装已支持；不支持的参数应明确拒绝。`work_dir`需位于项目树内，保证派生文件与来源账可定位。

design manifest中的 `stamp_audit` 是兼容旧阶段机的声明列表，完整图谱审计放在 `atlas_audit`，覆盖策略另存；旧阶段机要审计派生ID还需传真实rows及有限许可，不能因为声明形状正确就认定网页阶段已可通过。

## 9. 本轮 P2：把六条构图诊断变成条件规则

用户指出首栋“过了技法，没过构图”：均匀复制完整开间并未形成建筑主次。本轮沿用塔亭族进行构图改造，保留平铺基线作对照；没有把原用户作品中的切角族直接套在现有塔亭件上。

设计契约由 `src/paris_builder/atlas_composition.py` 表达，规则只含开间索引、建筑角色、等级、相对进退、节奏相位与宽度预留，不含源件ID或方块名。`HousePlan`新增`composition_profile`，`design.plan_for`暴露`grouped_pavilions`（atlas默认）和`flat_baseline`；源件选择与接缝落实仍归装配层。旧显式开间`build()`保留历史行为，不以新默认覆盖旧基线。

| 用户诊断 | P2设计目标与落实策略 | 当前验收边界 |
|---|---|---|
| 1. 六开间同平面、无分组与主次 | 每翼形成近角退后组、中央1bay凸体、中段退后组、末端1bay凸体；凸体向街外移1格，三组边界统一6格节距，较原4/5格节距增加2/1格 | 契约与实际导出分组、进退和完整预算须一致；待本轮收据 |
| 2. 贵族层与标准层全楼读感雷同 | 重点开间标记emphasized，让贵族通高窗、花箱与连续带呼应凸体；窗与带的进退按组保持一致 | 不声称已新增不存在的窗套升档件；主层能否成为主角需实际视觉评审 |
| 3. 老虎窗全白、烟囱孤墙无重心 | 凸体上排采用6格宽深颊板老虎窗对中，普通组保留普通等级；纯源五烟道簇旋转为沿街可读，锚在中央/端部焦点 | 烟道完整、坡脚接管和屋面交接须重测；待本轮收据 |
| 4. 无色彩焦点 | 仅用源件真实植物，按焦点作有限点缀；色彩服从分组而非随机散点 | 蓝灰百叶变体当前缺件，粉彩店面整套混编未实现，不编造已有色变能力 |
| 5. 塔亭同进退线、帽部融入屋面 | 塔亭外移1格；采用素材1真实链栏、望柱与细杆源冠形成高于屋脊的焦点 | 实际源冠、旋转、来源和尺寸要有派生账；不能依据旧“黑球尖饰”描述自造 |
| 6. 屋顶右侧白缺口与band端头碎片 | 窗、阳台、檐口、屋面随组进退；端墩、阶步与屋面交接显式收口，定位并修复缺口 | 必须从导出与近景看修复结果，不能靠放宽覆盖规则取消诊断 |

分组需要真实宽度。三条分组边界统一采用6格节距，而原节距按`(4,5,5,4)`和seed相位变化；每条边界增量为`6-base_pitch`，即1或2格。三边界累计增加3～6格，再加塔亭外移的1格原点余量，每翼动态预留为4～7格，不能使用固定四格估算。`composition.rhythm`保存节奏与phase，开间推导和装配必须使用同一相位。

正式plan CLI默认预算为宽46、深42，用于保留原P1的北6/西5开间数量，便于比较构图效果；原P1预算40×36得到实际39×35的平铺楼。本轮仍要求最终scene宽深不超过新预算，实际尺寸要从新导出量测。尺寸无法容纳目标开间与动态预留时，应拒绝或减少开间，不能无声扩张。

“有主有次”不能只靠提高顶端一点或多放几盆花。重点应同时控制平面凸退、宽柱分组、窗层级、老虎窗等级和烟囱重心；屋面/阳台/檐口需要一起响应，否则新方案会变成窗件前移而水平带断裂。

本轮预计候选目录为 `runs/ATLAS-PLAN-P2-v0.1/`，用于检验造型层规则如何驱动真实件装配，属于主流程的实现证据。它不能替代玩家任务的framework评审或整栋交付。本报告此处只记录当前实现方向；最终尺寸、开间、文件哈希、技术检查、重建、七视角观察和残余缺陷均待本轮收据，不能从P1或v0.2复制数字。

## 11. 符合性、建筑品质和最终游戏认可

项目采用“符合性由代码判，品质由模型/实际视觉评审判，最终认可由用户在游戏中判”的分工。可量测项包括尺寸、洞口位置/深度、共墙、坡折、屋脊、构件保留与接缝；不可将模型描述转成几何真值，也不可由有非空气邻接证明所有半砖/楼梯模型接触。

旧split-v3适配器的43个谓词适用于指定北/东临街、西/南盲墙的旧转角候选。新塔亭、北/西两翼和凸体构图必须用相应设计条件与量测，不能直接套旧规格或宣称与旧95项等价。unsupported应保持未支持，并阻止无目标修复。

视觉检查至少包含front、back、left、right、top和两个轴测，再补街面、转角、屋面近景。需要与源全景及代表件对比构造，也与现实风格证据比较组织；“像巴黎”和“符合用户Minecraft手法”都要成立。新候选的观察、缺陷与处理必须绑定同一最终哈希。

游戏阶段检查禁止更新粘贴后显示、薄门/墙肢/楼梯/栏杆冻结态、区块重载、实际相邻操作后的稳定性，以及街景、近景、屋面、共墙的审美。STATE-LAB用于状态实验；整栋用于建筑验收。系统不能把技术PASS、模型PASS或点击下载自动写为用户认可。

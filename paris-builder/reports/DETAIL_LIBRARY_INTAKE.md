## 2. 判定规则：按「类」分别判，不用一个阈值套所有

一开始我用一条规则（不同状态数 < 25 就排除），结果把 9 个窗单元全排除了——那是错的。
三个类别的性质完全不同：

- **实心填充类**（填充率 ≥ 0.95）：`房子0N[修改版]` 十个和 `巴黎民居街区1/2/3/5/6/7` 六个，
  填充率 0.979–0.999。这是掏空后剩下的**填充体**，内部没有细节可拆、没有开口可读。
  **排除 16 件。**
- **构件类**（包围盒每轴 ≤ 8）：`窗N` 九个。它们小，但**小不是缺陷**：有状态占比 0.25–0.77，
  而且九件各自用完全不同的材质族（桦木／丛林木／砂岩／泥砖／铁／带釉陶瓦）。
  这正是项目一直缺的多样构件语汇，**必须入库**。小尺寸不参与评分。
- **建筑类**（其余）：按技法判定。几乎全是无状态方块的建筑没有技法可学——但本次
  `房子01–10` 的有状态占比 0.073–0.077，**高于 0.06 的阈值**，所以入库；它们确实用了楼梯、
  活板门、栅栏门等构件，只是语汇简。这里必须诚实说明：**它们语汇简，与项目「不要照抄
  房子01–30 极简语汇」的告诫并不冲突**——告诫针对的是照抄外形，而本库只取其中的**构件**，
  且每一件都记录了来源与坐标，可以被追溯。

最终：**43 件源文件 → 28 件入库、15 件排除**（排除理由全部写在 `survey.json` 的
`exclusion_reasons` 与 `contributes_detail` 字段里，没有静默丢弃）。

## 3. 细节抽取：三次踩坑与修正

抽取的做法是：锚定「只有状态才能表达」的方块，从锚点向外连通生长，切出包围盒，去掉空气，
判读、规范化、记录来源。

| # | 症状 | 根因 | 修正 |
|---|---|---|---|
| 1 | 出现 190×55×125 的「窗」，392,453 格 | 锚点表里放了 `wall`/`stairs`/`slab`/`carpet`——它们覆盖整个立面，连通生长把整栋楼吃进来 | 锚点收窄到稀有方块（活板门、玻璃板、栅栏门、门、拉杆、活塞头…）；并给连通生长加**尺寸上限**，超限即停 |
| 2 | 仍是 20×5×5 的实心石块 | 生长穿过了周围石墙 | 用**锚点簇本身**当构件，只保留 1 格外扩；生长过程只允许锚点格 |
| 3 | 裁到 5×7×4 后，裁剪框又被撑到 19×6×24 | `seal_multicell` 在**全图**里找同名门，把整栋楼的门都拉进框 | 只允许**接触当前框**的门格拉框；并先按尺寸上限夹住锚点簇，再加外扩 |

## 4. 方块禁止更新：本轮最关键的一条

用户的说明：**有些手法是通过方块更新产出的；方块禁止更新。** 这两句合起来决定了导出件
必须自带状态，不能指望游戏重算。

判读结果（`runs/DETAIL-INTAKE-v0.1/frozen_check.json`）：**770/770 件在禁止更新下成立**，
0 幽灵墙肢（`up=false` 且四向 `none`）、0 不连接玻璃板。但**53,000 余格是有状态方块**，

### 门的两扇：一个真实缺陷与 687 格清洗

源作品里大量门被导出成**两格都是 `half=lower`**。原因是用户说明的那件事：建的时候游戏通过
方块更新把上扇纠正成 `upper`，导出成 `.schem` 时冻结的是那一刻的状态，两格都写着 lower。

在禁止更新环境下粘下去就是**两截半门**。所以导出件必须自己带正确配对。处理方式：

- 导出前把同列相邻的两格规范化为 `lower`/`upper` 配对，**共清洗 687 格**；
- 原始状态证据保留在每件的 `normalisations.original_door_states` 里；
- 裁剪边界切断、无法配对的门：**整件拒绝**（218 条排除里包含这类），理由写明
  「裁剪切断门：N 格无法配对（禁止更新下是半扇门）」，绝不留半扇门出厂。

清洗不等于篡改：改了哪一格、原状态是什么，都在记录里。

## 6. 尚未完成（不要当成已完成）

- **尚未接进 `technique.py`**：这 770 件目前只是入库并验证，还没被立面/技法层按开间、
  楼层、角色去选取。这是下一步，也是「像细节」真正落地的地方。
- **抽取上限**：`--limit-per-source 40` 使 20 个大源各只取到 40 件。提高上限还能取更多，
  目前是按需截取的，不是源里只有这些。
- **构件类源只取了 1–2 件**：9 个窗文件本身就是单元，每件只抽 1 个；如果需要它们各自的
  多种拆法，要另做按子结构的拆分。
- `shopfront` 与 `roof` 两类锚点本轮没有产出合格件（0 件），说明现存源里这两类细节的
  方块组合不满足最小状态数要求，或锚点表对该类不合适。**这是未解决的缺口**，
  不能因为库里有 770 件就当作细节已全。
- 语义命名仍是推断：库里记录的是**精确状态 + 来源坐标**，构件叫「窗」还是「檐口」是
  按锚点类别给的，不是从源里读出的语义。
- 游戏内验收：`game_acceptance` 始终 **PENDING**，只能由用户判定。

## 7. 命令

```powershell
cd paris-builder; $env:PYTHONPATH = 'src'

# 1) 测量与判定（写出 survey.json，含逐源排除理由）
python tools\survey_incoming.py --json runs\DETAIL-INTAKE-vX\survey.json

# 2) 抽取细节（--write-schem 会为每件导出独立 detail.schem）
python tools\extract_details.py --limit-per-source 40 --write-schem

# 3) 判读禁止更新下是否成立
python tools\check_frozen_details.py --json runs\DETAIL-INTAKE-vX\frozen_check.json
```

源文件归档在仓库根的 `_incoming_schematics/`（窗 / 民居街区 / 建筑素材 / 房子极简版）。
